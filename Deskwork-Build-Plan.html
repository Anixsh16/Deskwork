Major project · JIIT Noida · Build plan v3 · 22 Sep 2026

Deskwork. Set the paper, check the papers, clear the desk

One place for the work teachers still do by hand. Check handwritten answer booklets against an approved rubric, with evidence for every mark and the teacher in charge. Generate assignments and papers from the course's own slides. Ask a built-in assistant for help anywhere in the app. More tools follow.

Users Teachers only, any college Milestones Mid eval: working prototype · Final eval: finished product AI Gemini 3.5 Flash-Lite + 3.1 Flash-Lite, free tier Demo subject Whichever subject's material you share

§1Verdict

Two research agents reviewed the plan independently. One looked at it from the teacher, product and institution side. The other looked at the engineering and the Gemini API. Their joint conclusion, which I agree with:

The idea is good, as long as the pitch stays honest. "One AI grades everyone, so it is fair" won't survive a viva. Current research shows vision models change 50 to 64% of criterion marks when the same answer is graded again. They also quietly "fix" student mistakes while reading the handwriting.

The version you can defend: two independent models grade each booklet directly from the scanned image. Every mark cites visible evidence. When the models disagree, the answer goes to the teacher, and the UI makes sure the teacher actually reviews it. Around that sit an assignment generator grounded in the teacher's own slides and an assistant available everywhere. Pitch: "Deskwork does the repetitive work: checking, setting papers, drafting. The teacher stays the examiner and the author."

§3Product definition

Who

  • Teachers only, at any college. The demo uses JIIT material.
  • Students never log in. Papers and results still reach them through Google Classroom or WhatsApp.

Problem

  • Teachers still do checking, paper setting and drafting by hand.
  • Checking 60 to 200 booklets takes days, different checkers mark differently, and students dispute marks.
  • Writing fresh assignments and papers from slides eats hours every week.

Modules

ModuleMid evalFinal eval
Exam checking (headline feature)LIVE full flowDeeper grading, faster review
Assignment and paper generatorLIVE basicSets, Word export, per-question edits
Assistant (chatbot on every page)LIVE basic toolsMulti-step actions with confirmation
Lesson planner, question bank, feedback writer, rubric library, analyticsCOMING SOON visible in the UIBuilt as time allows

What makes it different

  • Two-model agreement instead of trusting one model, with every mark citing the student's own words.
  • Designed against automation bias: the UI makes the teacher actually look before accepting.
  • Grounded in the teacher's material: the generator and assistant work from the course's own slides, with page references.
  • Built for Indian exams: T1, T2 and End Sem booklets, half marks, supplementary sheets.
  • Free to run on the Gemini free tier for a class-sized batch.

Make it a real test set

  • Human marks: have a teacher (or a teammate, using the approved rubric) mark your answers. Without human marks there is no accuracy number.
  • More booklets: each team member hand-writes 3 to 5 answer booklets for the same paper, with deliberately planted errors recorded in a sheet. Plant a wrong step, a wrong unit, a missing definition, a crossed-out attempt, and an answer continued on a later page. Aim for 12 to 20 booklets.
  • Human baseline: two team members mark the extra booklets blind with the approved rubric. The AI-vs-human gap is then compared with the human-vs-human gap.
  • Cover all four types: include at least one theory, one numerical, one code and one diagram question. If the provided paper lacks a type, add a question to the extra booklets.

§9AI calls and prompts

There are six call types. C1 to C5 run in the worker through ai/client.py, which throttles, retries, falls back to the other model, caches, and logs usage. C6 is the assistant route. Prompts live in versioned files, so the cache key changes whenever a prompt changes.

C2 build_rubricQuestions plus typed key text or handwritten key page imagesCriteria per question (0.5 to 3 marks each), final answers, alternatives, and the key transcript3.5 / medium1 per exam

Model settings (checked against the Gemini docs by the research agent)

  • Model IDs: gemini-3.5-flash-lite and gemini-3.1-flash-lite. Both take 1M input tokens and return up to 64k.
  • Do not set temperature, top_p or top_k. Google recommends the defaults for Gemini 3; a low temperature can make the model loop.
  • thinking_level: minimal is the Flash-Lite default. Use low for extraction and the assistant, and medium for grading and rubrics. Pick the final values with the harness.
  • media_resolution: high (about 1,120 tokens per image) for handwriting. Try medium in the harness to save tokens.
  • Use structured output with a JSON Schema generated from Pydantic, and keep schemas shallow.
  • Don't store slides in the Files API, because files expire after 48 hours. Context caching isn't on the free tier either, so send extracted text instead.
# worker/deskwork_worker/ai/client.py  (sketch; confirm field names against current google-genai docs)
from google import genai
from google.genai import types

client = genai.Client()  # reads GEMINI_API_KEY

def call_json(model, system, parts, schema_model, thinking="medium", media="high"):
    key = cache_key(model, system, parts, schema_model)
    if (hit := cache_get(key)): return hit
    bucket.acquire(model, est_tokens(parts))          # RPM + TPM token bucket per model
    resp = with_retry(lambda: client.models.generate_content(
        model=model,
        contents=parts,
        config=types.GenerateContentConfig(
            system_instruction=system,
            response_mime_type="application/json",
            response_json_schema=schema_model.model_json_schema(),
            thinking_config=types.ThinkingConfig(thinking_level=thinking),
            media_resolution=f"MEDIA_RESOLUTION_{media.upper()}",
        )))                                           # retry 429/503: exp backoff + jitter, max 5
    data = schema_model.model_validate_json(resp.text)   # one re-ask on validation failure
    cache_put(key, model, data); usage_inc(model, "worker", resp.usage_metadata)
    return data
# generate_content is the long-supported path; the newer Interactions API also works.
# If using Interactions, check whether it stores data server-side by default and turn that off.

Schemas (Pydantic models, converted to JSON schema)

class RubricCriterion(BaseModel):
    key: str                      # "q2a.c1"
    description: str
    marks: float                  # 0.5 to 3, steps of 0.5
    accept_alternatives: list[str] = []
    common_errors: list[str] = []

class RubricQuestion(BaseModel):
    label: str
    criteria: list[RubricCriterion]
    final_answer: str | None = None
    tolerance_pct: float | None = None
    units: str | None = None

class RubricDraft(BaseModel):
    key_transcript: str           # what the model read from the key (teacher checks this)
    questions: list[RubricQuestion]

class PageInfo(BaseModel):
    page: int
    questions: list[str]
    legible: Literal["good", "partial", "poor"]

class CriterionScore(BaseModel):
    key: str
    evidence: str                 # quote or describe the student's own work FIRST
    points: float                 # clamped in code to [0, marks], rounded to 0.5

Flag = Literal["cross_page","crossed_out","diagram","code","illegible",
               "unanswered","alt_method","possible_misread"]

class AnswerGrade(BaseModel):
    label: str
    pages: list[int]
    transcript: str               # verbatim, keep errors, [crossed], [illegible]
    final_answer: str | None = None
    criteria: list[CriterionScore]
    flags: list[Flag] = []
    confidence: float             # 0 to 1

class BookletGrade(BaseModel):
    pages: list[PageInfo]
    answers: list[AnswerGrade]

Grading system prompt (prompts/grade_booklet.v1.md)

You are an exam checker applying an approved rubric to one student's scanned answer booklet.
Pages are labelled "PAGE n". The student is anonymous.

Rules:
1. Grade only what is visibly written. Never assume what the student meant.
2. Do NOT correct the student's errors, even small ones, in the transcript or in your judgement.
   A wrong sign, wrong unit or wrong step stays wrong.
3. Ignore handwriting neatness, grammar, spelling and answer length. Judge content only.
4. Crossed-out work is withdrawn and earns nothing, unless nothing else is written for that part.
5. Answers may be out of order or continue on later pages. Use question labels written by the
   student to build the page map. If a label is missing, infer from content and add "possible_misread".
6. For each rubric criterion: first write evidence (quote or describe the student's work),
   then award points from 0 to that criterion's marks in steps of 0.5.
7. Accept any method listed in accept_alternatives, and any other correct method (flag "alt_method").
8. If a question is not attempted, return it with 0 points and flag "unanswered".
9. Always flag "diagram" for drawings and "code" for program code.
10. confidence = how sure you are the awarded points match what an expert examiner would give.

Return JSON matching the schema. Include every question in the rubric.

Parts are sent in this order: the system prompt, then the approved rubric JSON (with question text, max marks and answer type), then each page as the text "PAGE n" followed by its image.

Rules enforced in code, never trusted from the model

  • Clamp each criterion to [0, marks], round to 0.5, and recompute the question totals and booklet total.
  • Reject criterion keys that aren't in the rubric. A missing criterion counts as 0 and adds a flag.
  • Numeric questions: parse final_answer and compare it with the key within tolerance_pct. If they don't match but the model awarded the final-answer criterion, add the flag numeric_mismatch.

§10Grading pipeline, step by step

flowchart TD
  A[Teacher uploads paper] --> B[C1 extract questions]
  B --> C[Teacher edits questions, marks, type]
  C --> D[Upload typed or handwritten key]
  D --> E[C2 draft rubric + key transcript]
  E --> F[Teacher edits and approves: frozen rubric version]
  F --> G[Upload booklets]
  G --> H[Render pages, mask name locally, page count + blur check]
  H --> I[C3 grader A: 3.5 Flash-Lite, whole booklet]
  H --> J[C4 grader B: 3.1 Flash-Lite, whole booklet]
  I --> K[Compare, validate, flag]
  J --> K
  K --> L[Review queue: flagged first]
  L --> M[Teacher reviews, spot-checks 10%, bulk-accepts rest]
  M --> N[Final marks, audit log, Excel]

Flag rules (finalize_flags job)

A question in a booklet is flagged if any of these is true:

  • Graders A and B differ by 1 mark or more on any criterion, or by 1.5 or more on the question total.
  • Either grader's confidence is below 0.7.
  • The answer type is code or diagram.
  • It carries any of these flags: cross_page, crossed_out, illegible, possible_misread, alt_method, numeric_mismatch.
  • A page it sits on scored below the blur threshold, or the booklet failed the page-count check.
  • The AI awarded less than 40% of max marks. Harsh AI errors are the ones teachers miss most.

For unflagged questions, ai_marks is the mean of A and B rounded to 0.5, and the status is pending. Flagged questions get the status flagged, and both graders' views are stored for the review screen.

CLAIM = """
update jobs set status='running', locked_at=now(), attempts=attempts+1
where id = (select id from jobs where status='queued' and run_after<=now()
            order by id for update skip locked limit 1)
returning *;"""
while True:
    job = db.fetchone(CLAIM)
    if not job: sleep(2); continue
    try:
        HANDLERS[job.kind](job.payload, progress=lambda p: set_progress(job.id, p))
        mark_done(job.id)
    except RateLimited as e:

    except Exception as e:
        fail_or_retry(job.id, e, max_attempts=3)

§11Assistant chatbot

A chat panel that opens from any page (Cmd + J, or the button at the bottom right). It knows which course or exam the teacher is looking at. It works through a small set of tools, never by querying the database freely.

How it works

  • Route: app/api/assistant/route.ts streams replies using @google/genai with function calling. The Gemini key stays on the server.
  • Context sent with each message: the current route, the course or exam id and title, and the last 10 messages of the thread.
  • Tools run with the teacher's own Supabase session, so RLS limits them to that teacher's data.
  • Read-only in the prototype. Anything that would change data returns a link or a pre-filled form, and the teacher clicks the final button.
  • Limits: at most 2 tool rounds per message, so each message costs 1 to 3 calls. Usage is logged in ai_usage_daily with source='assistant'.
  • Citations: answers drawn from slides show chips like "Unit 2 slides, p. 14" that open the page.
  • Privacy: results tools return anon IDs only. Names are never sent to the model.

§16Evaluation harness

Metrics

  • Per criterion: exact agreement, agreement within 0.5, MAE
  • Per question: MAE, within-1 accuracy, QWK (cohen_kappa_score(weights="quadratic"))
  • Per booklet total: MAE, Pearson r, bootstrap 95% CI (1,000 samples)
  • Agreement between graders A and B, and the human-vs-human baseline
  • Run-to-run stability over 3 runs (% of criteria that change)
  • Planted-error detection rate (catches over-correction)
  • Flag precision and recall against cases where the AI differs from the human by 1 mark or more
  • Transcription character error rate (CER) on 5 hand-typed pages

Breakdowns and experiments

  • Every metric split by answer type: theory, numeric, code, diagram
  • Calls, tokens and seconds per booklet
  • Experiments: media resolution medium vs high; thinking level low vs medium; with vs without one graded anchor example; 3.5 alone vs A+B agreement
  • Reports written to eval/reports/<date>.md, with tables ready for the synopsis

Report honestly. A result like "theory answers are within 1 mark 85% of the time, code only 40%, so code always goes to the teacher" is stronger at a viva than one inflated accuracy number.

§17Privacy and ethics

  • Demo data: your own handwritten answers, used with your full consent, plus booklets the team writes.
  • Masking: the worker paints over the name and roll-number box before any AI call. Names never appear in prompts; the AI and the assistant only see S001, S002 and so on.
  • Free-tier caveat, stated openly: Google may use free-tier inputs and have humans review them. For real classroom use, the setting GEMINI_TIER=paid points to a paid key whose data isn't used for training.
  • Teacher is the examiner: nothing becomes final or exportable as final until the teacher has reviewed it or bulk-accepted it, with an audit trail.
  • Assistant limits: read-only in the prototype, scoped by RLS, and it never sees student names.
  • DPDP basics: a privacy notice at sign-up, data used only for the stated purpose, and a "Delete exam and all scripts" button that removes both the stored files and the database rows.
  • Bias: the grading prompt tells the model to ignore neatness, grammar and length, and the harness tests this with planted style variations.

Questions the panel will ask

QuestionAnswer
What if the AI is wrong?It never finalises a mark. Two models have to agree. Disagreements, low confidence, harsh marks, code and diagrams all go to the teacher, and the UI makes sure the teacher really looks. Our measured agreement is X, broken down by answer type.
Is it actually fair?Every booklet is graded against the same approved rubric, with names hidden. Each mark cites its evidence, and every change is in the audit log. That's more consistent than several different checkers, and fully explainable on script-showing day.
What about student privacy?Names are masked on our side before the AI sees anything. The demo uses consented data. Real use moves to a paid tier that doesn't train on data. There's a privacy notice and a delete option.
How is this different from Gradescope or MagicSchool?It combines checking, generation and an assistant in one workspace grounded in the teacher's own slides. It verifies marks with two models, is designed against automation bias, is built for Indian booklets, and is free to run.
What about CBSE's scanning problems?We check page count and blur at upload and tag every page with its booklet ID. Nothing is published automatically.
Can the assistant break things?Not in the prototype: it's read-only and limited to the teacher's own data. In the final version, every action needs the teacher to confirm it.
Why teachers only?The teacher is the accountable examiner, and distribution to students already happens through Classroom and WhatsApp.
